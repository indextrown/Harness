# Evals and Observability

좋은 하네스는 구현 전에 검증과 관측을 설계합니다.

이 문서는 `awesome-harness-engineering`에서 강조하는 평가와 관측 축을 저장소 운영 규칙으로 번역한 것입니다.

## 왜 먼저 설계하나

- 에이전트는 빠르게 많은 코드를 만들 수 있다.
- 사람의 주의력은 병목이 되기 쉽다.
- 따라서 품질 확인을 사람 감각에만 맡기면 확장되지 않는다.

## 최소 검증 계층

실제 코드가 추가되면 아래 계층을 가능한 한 기계적으로 채웁니다.

1. 정적 검증
2. 단위 검증
3. 통합 검증
4. 핵심 사용자 여정 스모크 검증
5. 회귀 검증

## 평가 설계 규칙

- 작업 성공 여부를 모호한 인상 대신 명시적 기준으로 표현한다.
- 가능하면 "수정 전 실패, 수정 후 성공" 형태를 만든다.
- 같은 작업을 반복 측정할 수 있게 입력과 기대 결과를 남긴다.
- 도구나 스킬이 실제로 도움이 되는지 `없을 때 대비` 기준으로도 본다.

## 관측 포인트

앱이나 서비스가 생기면 다음을 설계합니다.

- 로그: 어떤 실패가 어디서 났는지 빠르게 찾을 수 있어야 한다
- 메트릭: 속도, 오류율, 리소스 사용량 같은 경향을 볼 수 있어야 한다
- 추적: 여러 단계가 이어지는 요청의 병목을 볼 수 있어야 한다
- UI 증거: 스크린샷, DOM 상태, 사용자 여정 결과를 남길 수 있어야 한다

핵심은 에이전트에게 "눈"을 달아주는 것입니다. 사람이 직접 모든 화면과 출력을 대신 봐주는 구조는 오래 가지 않습니다.

## 실행 전 체크리스트

- 어떤 명령이 성공을 증명하는가
- 어떤 실패가 예상 가능한가
- 어떤 로그 또는 스크린샷이 증거가 되는가
- 어느 수준까지 자동화하고 어느 부분을 사람이 본다

## 저장소 반영 방법

- 검증 명령은 `docs/QUALITY_SCORE.md`와 실제 스크립트에 반영합니다.
- 사용자 여정은 `docs/product-specs/`와 연결합니다.
- 반복 측정이 필요한 검증은 별도 평가 하네스로 승격합니다.
- 로그, 스크린샷, 검증 산출물은 `logs/` 같은 명시적 위치에 남길 수 있게 준비합니다.
