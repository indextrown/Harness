# Harness Evolution

하네스는 한 번 설계하고 끝나는 정적 문서가 아닙니다.

이 문서는 `revfactory/harness`의 진화 메커니즘 개념을 Codex 작업 저장소에 맞게 옮긴 규칙입니다.

## 핵심 생각

이번 실행에서 먹힌 것과 먹히지 않은 것의 차이를 기록해야 다음 실행이 더 좋아집니다.

## 진화 루프

1. 초기 하네스로 작업을 시작한다.
2. 실제 구현과 검증을 수행한다.
3. 마찰이 생긴 지점을 기록한다.
4. 문서, 템플릿, 체크리스트, 스크립트로 되먹인다.
5. 다음 작업은 더 나은 기본값에서 시작한다.

## 무엇을 포착할까

- 에이전트가 반복해서 놓친 제약
- 설명만으로는 부족했던 규칙
- 자주 실패한 검증 절차
- 길고 비싼 탐색을 줄여준 링크나 템플릿
- 사람 리뷰에서 반복적으로 등장한 피드백

## 되먹임 대상

- `AGENTS.md`: 진입 규칙이 부족했을 때
- `docs/ARCHITECTURE.md`: 구조 제약이 부족했을 때
- `docs/templates/`: 매번 비슷한 작업 브리프를 쓸 때
- `docs/EVALS_OBSERVABILITY.md`: 검증 기준이 약했을 때
- 스크립트와 린터: 설명보다 강제가 필요할 때

## 항상 확인할 것

하네스 엔지니어링 업데이트가 있었다면 다음 질문을 반드시 확인합니다.

- 이번 변경으로 에이전트의 첫 진입 경로가 바뀌었는가
- 새 문서, 명령, 스크립트, 훅이 생겼는가
- 그렇다면 `AGENTS.md`가 그 변화를 반영하고 있는가

답이 하나라도 아니오라면, 하네스 업데이트는 아직 끝나지 않은 것입니다.

## 최소 진화 기록 형식

작업이 끝날 때 아래 네 줄 정도는 남깁니다.

- 무엇이 잘 작동했는가
- 어디에서 마찰이 있었는가
- 다음부터 기본 규칙으로 올릴 것은 무엇인가
- 문서로 남길지 툴링으로 강제할지

## 목표

하네스를 더 길게 만드는 것이 목표가 아닙니다. 더 짧은 설명으로 더 안정적인 실행을 가능하게 만드는 것이 목표입니다.
