# Context Engineering

하네스 품질은 종종 모델보다 컨텍스트 설계에 더 크게 좌우됩니다.

이 문서는 긴 작업에서 컨텍스트를 버리지 않고 유지하기 위한 기본 규칙을 정의합니다.

## 목표

- 불필요한 정보로 컨텍스트를 오염시키지 않는다.
- 현재 작업에 필요한 사실만 빠르게 찾게 한다.
- 긴 실행 이후에도 다음 실행이 이어받을 수 있게 한다.

## 기본 원칙

- 컨텍스트는 무한 저장소가 아니라 작업 메모리다.
- 큰 문서 하나보다 짧은 색인과 링크된 세부 문서가 낫다.
- 실패 로그도 가치가 있으면 남기고, 잡음이면 요약해서 버린다.
- 임시 대화보다 버전 관리되는 파일이 더 신뢰할 수 있다.
- 너무 많은 지침은 지침이 아니라 소음이 된다.

## 실무 규칙

- 저장소 진입 규칙은 `AGENTS.md`에 짧게 둔다.
- 도메인 지식은 `docs/` 하위의 주제별 문서로 분리한다.
- 작업 상태는 `docs/exec-plans/active/`의 계획 파일에서 관리한다.
- 큰 로그나 긴 출력은 원문 전체 대신 요약과 핵심 결론만 남긴다.
- 다음 실행에 꼭 필요한 실패 원인과 재현 단계는 문서로 승격한다.

## 점진적 공개

에이전트는 처음부터 모든 문서를 읽지 않는다.

1. `AGENTS.md`로 진입한다.
2. 현재 작업과 직접 관련된 상위 문서를 읽는다.
3. 더 깊은 정보가 필요할 때만 하위 문서나 참고 자료를 읽는다.
4. 작업이 끝나면 다음 실행이 같은 탐색을 반복하지 않게 링크를 보강한다.

이 방식은 "큰 지침 파일 하나를 다 읽게 하기"보다 "목차를 주고 필요한 문서를 찾아가게 하기"에 가깝다.

## 컨텍스트 드리프트 징후

- 이미 존재하는 규칙을 모른 채 새 규칙을 덧붙인다.
- 같은 문제를 다른 파일에서 서로 다르게 설명한다.
- 작업 중반부터 목표보다 구현 세부에만 매몰된다.
- 실패 원인을 잊고 같은 실험을 반복한다.

## 대응 방법

- 목표, 제약, 검증 기준을 계획 파일 상단에 다시 적는다.
- 오래된 문서를 새 문서로 덮지 말고 기존 문서를 수정한다.
- 중요한 결정은 `의사결정 로그` 섹션에 즉시 남긴다.
- 실패 실험은 버릴지, 참고용으로 보존할지 분명히 결정한다.
