# Harness

이 저장소는 Codex 기반 에이전트 우선 엔지니어링을 위한 시작용 하네스입니다.

목표는 단순히 코드를 저장하는 것이 아닙니다. 에이전트가 다음을 할 수 있는 환경을 만드는 것이 목적입니다.

- 저장소를 빠르게 이해하고,
- 올바른 제약을 발견하고,
- 작은 검증 루프 안에서 변경을 실행하고,
- 다음 실행을 위해 더 나은 맥락을 남기도록 만드는 것

## 이 저장소가 지향하는 것

이 하네스는 단순한 "프롬프트 모음"이 아닙니다. 아래 네 층을 함께 관리하는 저장소를 목표로 합니다.

- 지도 층: `AGENTS.md`처럼 짧은 진입 문서
- 지식 층: `docs/` 아래의 구조화된 문서와 템플릿
- 실행 층: 계획, 검증, 체크리스트, 스크립트
- 진화 층: 무엇이 잘 먹혔고 무엇이 실패했는지를 다음 실행에 되먹이는 기록

## 구조

- `AGENTS.md`: 에이전트를 위한 짧은 진입 문서
- `docs/`: 오래 유지되는 지식 베이스와 운영 규칙
- `docs/exec-plans/`: 진행 중이거나 완료된 실행 계획
- `docs/task-requests/`: 작업 요청서 보관소
- `docs/templates/`: 계획, 명세, 작업 브리프 템플릿
- `project/`: 실제 개발 파일이 들어갈 공식 구현 디렉터리

## 운영 아이디어

이 하네스는 OpenAI의 하네스 엔지니어링 글에서 영감을 받은 몇 가지 원칙을 따릅니다.

- `AGENTS.md`는 짧고 지도처럼 유지합니다.
- 오래 유지되어야 하는 지식은 구조화된 `docs/` 체계로 옮깁니다.
- 계획은 저장소 안의 일급 아티팩트로 다룹니다.
- 인간의 취향만이 아니라 에이전트의 가독성에도 최적화합니다.
- 반복되는 리뷰 피드백은 명시적 규칙이나 템플릿으로 승격합니다.
- 하네스 구조가 바뀌면 `AGENTS.md`를 함께 갱신해 진입 문서를 항상 최신 상태로 유지합니다.

추가로, 두 개의 외부 참고축을 이 저장소에 흡수했습니다.

- `awesome-harness-engineering`: 하네스 엔지니어링을 컨텍스트, 가드레일, 평가, 관측, 런타임으로 분류하는 참조 카탈로그 관점
- `revfactory/harness`: 작업을 에이전트 팀 패턴, 스킬, 검증, 진화 메커니즘으로 구조화하는 팩토리 관점

이 저장소는 Claude 전용 플러그인 구조를 그대로 복제하지는 않습니다. 대신 그 관점을 Codex 작업 저장소에 맞게 번역하여 다음 요소로 재구성합니다.

- 작업 유형에 따라 선택하는 팀 아키텍처 패턴
- 긴 실행을 위한 컨텍스트 관리 원칙
- 검증과 관측을 먼저 설계하는 운영 문서
- 실행 결과의 델타를 기록하는 하네스 진화 루프

## 핵심 문서

- `docs/PROMPT_CONTEXT_HARNESS.md`: 프롬프트, 컨텍스트, 하네스의 차이와 역할
- `docs/COMMANDS.md`: 이슈, 계획, 워크트리, 검증, 병합 명령 모음
- `docs/TASK_REQUESTS.md`: 무엇을 할지 먼저 고정하는 작업 요청서 운영 방식
- `docs/TEAM_ARCHITECTURES.md`: 어떤 작업에 어떤 팀 구조를 쓸지 정리
- `docs/CONTEXT_ENGINEERING.md`: 긴 작업에서 문맥 드리프트를 줄이는 규칙
- `docs/EVALS_OBSERVABILITY.md`: 검증, 평가, 관측 설계
- `docs/HARNESS_EVOLUTION.md`: 하네스를 스스로 개선하는 루프
- `docs/WORKTREE_WORKFLOW.md`: 메인 대신 워크트리에서 작업하는 운영 규칙
- `docs/VERIFY_AND_GUARDRAILS.md`: 말이 아니라 검증과 훅으로 강제하는 규칙
- `docs/VISIBILITY_AND_LOGS.md`: 로그, 스크린샷, 검증 흔적을 남기는 규약
- `docs/REFERENCES.md`: 외부 참고 자료와 왜 중요한지

## 권장 작업 흐름

1. `AGENTS.md`와 관련 문서를 읽고 진입합니다.
2. 작업이 중간 이상 규모라면 `docs/task-requests/active/`에 작업 요청서를 먼저 작성합니다.
3. 이어서 `docs/exec-plans/active/`에 계획을 작성합니다.
4. 가능하면 메인에서 바로 수정하지 말고 워크트리 기반 작업 흐름을 사용합니다.
5. 필요한 경우 `docs/templates/` 템플릿으로 명세와 브리프를 만듭니다.
6. 구현 전에 검증 방식과 관측 포인트를 먼저 정합니다.
7. `scripts/`의 검증 스크립트나 체크 스크립트로 규칙을 강제합니다.
8. 완료 후 결과와 교훈을 계획 또는 설계 문서에 반영합니다.

## 구현 파일 배치 원칙

- 기능 코드와 앱 코드는 루트에 직접 추가하지 않습니다.
- 실제 개발 파일은 `project/` 하위에만 둡니다.
- 구현 루트 결정은 `docs/ARCHITECTURE.md`에 기록합니다.

## 추천 다음 단계

1. 실제 앱 또는 서비스 코드를 `project/` 아래에 추가합니다.
2. 실행 가능한 검증 명령을 추가하고 이를 `docs/QUALITY_SCORE.md`에 문서화합니다.
3. 프로젝트 전용 아키텍처 제약을 `docs/ARCHITECTURE.md`에 구체화합니다.
4. 제품 명세를 `docs/product-specs/`에 추가합니다.
5. 단순하지 않은 작업은 `docs/exec-plans/active/`의 파일로 시작합니다.
